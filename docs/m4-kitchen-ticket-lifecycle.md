# M4.2/M4.3 — Order Integration and Kitchen Ticket Lifecycle

M4.2 connects the M4.1 kitchen storage to the M3 staff order workflow. It adds
atomic ticket generation on order acceptance, independent ticket-item
preparation state, ticket aggregation, cancellation propagation, audit records,
and secure transition RPCs.

M4.3 adds the application-facing KDS read model, station/routing management
RPCs, the kitchen Realtime publication, and the order-versus-kitchen state
ownership policy. It does **not** add a KDS frontend, ticket priority,
acknowledgement state, recall/reopen, station transfer, kitchen-side item
cancellation, or station-level staff assignment.

It does **not** add realtime subscriptions in the frontend, station management
UI, station-specific staff assignments, guest-ordering integration, or
hosted-database changes.

The M4.1 schema and authorization foundation is described in
[`m4-kitchen-infrastructure.md`](./m4-kitchen-infrastructure.md).

## 1. Ticket generation

Tickets are generated by database triggers within the transaction that accepts
the order. There is no client-callable generation RPC.

| Trigger | Event | Behavior |
| --- | --- | --- |
| `orders_generate_and_cancel_kitchen_tickets` | `AFTER UPDATE OF status ON public.orders` | On `accepted`, resolve routing for every non-cancelled order item. On `cancelled`, cancel kitchen tickets and items. |
| `order_items_generate_kitchen_tickets` | `AFTER INSERT ON public.order_items` | If the parent order is already `accepted`, route only the new item. |
| `order_items_cancel_kitchen_tickets` | `AFTER UPDATE OF status ON public.order_items` | On cancellation, cancel the matching ticket item(s) and recalculate affected tickets. |

Because generation happens in the acceptance transaction:

- A failed generation aborts the acceptance; the order is not left accepted
  without its tickets.
- Unrouted items are skipped rather than failing acceptance.
- Repeated or concurrent acceptance cannot leave a partially generated order.

Ticket identity is generation-based. `kitchen_tickets` has one **active** ticket
per `(order, station)`, enforced by a partial unique index over non-cancelled
tickets. Cancelled tickets retain their own `generation` row as immutable
history. If every item for a station is cancelled and later work is added to the
same accepted order, generation creates the next generation instead of reopening
or reusing the cancelled ticket. Generation also locks the order row first, so
ticket identity cannot race order-item edits.

The M3 `transition_order_status` function is unchanged. M4.2 only adds
`AFTER` triggers.

## 2. Routing precedence

For each non-cancelled order item in the accepted order, routing is resolved
inside the item's organization and branch:

1. If at least one item-level route exists for the menu item in the branch, use
   the **active** item-level station routes. Item-level routing is exclusive:
   category routing is not added and is not used as a fallback.
2. Otherwise, use the **active** category-level station routes for the item's
   menu category in the branch.
3. Otherwise, the item is **unrouted**. No ticket or ticket item is created, and
   the order item remains valid and visible to the POS.

Inactive stations are filtered out after precedence is chosen. Therefore an
item with an item-level route to an inactive station is unrouted; it does not
fall back to an active category route.

The M4.1 schema permits more than one route to be configured for the same item
or category. When multiple active routes match, the item appears once on each
matching station's ticket. This is how one order can require several stations.
An order may therefore contain both routed and unrouted items.

## 3. Idempotency and concurrency

Generation is idempotent:

- `kitchen_tickets` has `unique (order_id, station_id, generation)`, and a
  partial unique index enforces at most one non-cancelled ticket per
  `(order_id, station_id)`. Generation reuses the active ticket when one exists.
  When no active ticket exists, it assigns `max(generation) + 1` and inserts with
  `ON CONFLICT (order_id, station_id, generation) DO NOTHING`. Cancelled tickets
  are never reopened.
- `kitchen_ticket_items` has `unique (ticket_id, order_item_id)`. Generation uses
  `INSERT ... ON CONFLICT (ticket_id, order_item_id) DO NOTHING`, preserving the
  original ticket-item identity.
- The existing M3 acceptance path already locks the order row for update, so
  concurrent acceptance attempts serialize. The losing attempt fails with the
  existing `ORDER_INVALID_STATUS` error and does not create tickets. M4.2
  generation also locks the order row, so item additions and removals serialize
  with ticket identity changes.
- Concurrent generation for the same order is additionally protected by the
  active-ticket partial index and generation key.
- Audit is written by insert/update triggers, so a retry that inserts nothing
  does not create duplicate ticket-created audit events.

Adding a new item to an order that is still `accepted` routes only that item;
existing active tickets and ticket items are not recreated or duplicated. If the
station's previous ticket was cancelled, a new generation is created.

## 4. Independent kitchen item state

`kitchen_ticket_items` now has its own preparation state:

| Column | Purpose |
| --- | --- |
| `status` | `pending`, `preparing`, `ready`, `completed`, or `cancelled`. |
| `started_at` | First time preparation began. |
| `ready_at` | Time the item became ready. |
| `completed_at` | Time kitchen processing completed. |
| `cancelled_at` | Cancellation time. |
| `cancelled_by_actor_type` | `staff` or `system`. |
| `cancelled_by_staff_id` | Cancelling staff actor for `staff`; null for `system`. |
| `cancellation_reason` | Reason copied from the order/order-item cancellation workflow. |

`kitchen_tickets` also carries `generation` and `cancelled_by_actor_type`. The
generation distinguishes historical cancelled tickets from current active work.

`order_items.status` remains the M3 order-lifecycle state. The kitchen state is
separate so that M3's order-status cascade cannot overwrite kitchen progress.
This is the smallest additive change that satisfies independent preparation
without rewriting M3.

Direct ticket-item writes are a privileged/trusted-write boundary. Authenticated
clients have `SELECT` only; all normal writes go through the lifecycle RPCs,
order triggers, or cancellation triggers. The database still maintains the
parent aggregate for direct item-status writes and rejects active items under a
cancelled ticket. Direct writes are not a supported application API.

Allowed item transitions:

```text
pending -> preparing -> ready -> completed
```

Additional rules:

- Skipped transitions are rejected (for example `pending -> ready`).
- Backward transitions are rejected (for example `ready -> preparing`).
- `cancelled` is accepted from any non-cancelled state when a cancellation
  actor and non-empty reason are supplied. Cancellation is terminal.
- Completed kitchen items cannot be cancelled by item removal. Whole-order
  cancellation is the only workflow that may cancel completed kitchen work.
- Repeating the current target status is a safe no-op for the RPCs.
- There is no client-callable path to `cancelled`; cancellation comes from the
  order/order-item cancellation workflow.
- A cancelled ticket or cancelled ticket item cannot be changed.

## 5. Ticket aggregation

After every item transition or cancellation, the ticket status is recalculated
from its non-cancelled items:

| Condition | Ticket status |
| --- | --- |
| Every non-cancelled item is `completed` | `completed` |
| Every non-cancelled item is `ready` or `completed` | `ready` |
| At least one non-cancelled item is `preparing`, `ready`, or `completed` | `preparing` |
| All non-cancelled items are `pending` | `pending` |
| Every item is `cancelled` | `cancelled` |
| Ticket has no items | Left unchanged (safe empty-ticket behavior) |

- `cancelled` is terminal; aggregation never turns a cancelled ticket into
  `completed` or reopens it.
- Ticket timestamps are set the first time the status reaches
  `preparing`/`ready`/`completed` and are not cleared.
- Aggregation is derived from current items. If a progressed item is later
  cancelled, or a new pending item is added to an existing accepted order, the
  ticket can move to a lower aggregate state that matches the remaining items.
- The ticket guard rejects any persisted status that does not exactly match the
  active-item aggregate. A privileged direct write cannot mark an incomplete
  ticket `ready`/`completed`, cannot regress a completed ticket to an incomplete
  aggregate, and cannot cancel a ticket while active items remain.
- An `AFTER INSERT OR UPDATE OF status` trigger on `kitchen_ticket_items`
  recalculates the parent ticket for direct item writes. An active item cannot
  be inserted into a cancelled ticket; new work must use a new generation.
  During whole-order cancellation, the cancellation function owns the final
  ticket update and the item trigger does not recalculate intermediate states.
- Empty tickets are explicitly non-aggregatable. They are left unchanged by
  recalculation; a direct status change to a non-cancelled state is rejected.
  Direct cancellation of an empty ticket is allowed only with valid attribution.
- Whole-order cancellation cancels the ticket items first and then the ticket, so
  it remains compatible with the exact aggregate guard.

## 6. Cancellation behavior

**Order cancellation**

When `cancel_order` moves the order to `cancelled` (or a privileged path does the
same with the required attribution), M4.2:

- cancels every non-cancelled ticket item for the order;
- cancels every non-cancelled ticket for the order;
- copies the order's cancellation actor and reason;
- records the actor domain as `staff` (with a staff id) or `system` (no staff id);
- never uses the order submitter as a cancellation-actor fallback;
- never marks a ticket `completed` as a result of cancellation.

A ticket that had already completed its items is recorded as `cancelled` with
the order cancellation attribution; the audit trail retains the earlier
completion transitions. Whole-order cancellation is the only path permitted to
cancel completed kitchen items.

**Order-item cancellation**

Removing or cancelling one order item cancels only the matching ticket item(s).
The affected ticket is recalculated and becomes `cancelled` only when all of its
items are cancelled. Unaffected tickets keep their current state.

- Removal is allowed while the order is `pending`, `accepted`, `preparing`, or
  `ready`, provided every matching kitchen item is `pending`, `preparing`, or
  `ready`. An unrouted item has no matching kitchen item and is treated as having
  no completed kitchen work. The order's own status is not changed by the
  removal.
- Removal is rejected once any matching ticket item is `completed`, or when the
  order is `served`, `completed`, or `cancelled`.
- Multi-station items cancel all matching station ticket items together, or the
  entire removal is rejected atomically if any matching item is completed.
- The order subtotal is recalculated through a transaction-local, narrowly
  scoped exception to the M3 order snapshot guard. This does not make order
  totals generally editable after preparation starts.
- Cancellation attribution becomes immutable once recorded. Changes to
  `cancelled_by_actor_type`, `cancelled_by_staff_id`, `cancelled_at`, or
  `cancellation_reason` on a cancelled ticket or ticket item are rejected.

Cancellation attribution is explicit. Staff-initiated cancellation records the
acting staff id and `cancelled_by_actor_type = 'staff'`. System-initiated
cancellation records `cancelled_by_actor_type = 'system'` with a null staff id.
A non-empty cancellation reason is always required.

## 7. Inactive stations and routing visibility

- Deactivating a station prevents new tickets from being routed to it.
- Existing tickets remain readable, because the M4.1 RLS policies are
  branch-scoped and do not depend on station status.
- Existing tickets remain completable; the item RPCs do not require an active
  station.
- Station deactivation does **not** cancel existing tickets.
- Reactivating a station restores its existing item/category routes for future
  routing.

An inactive **item-level** route still suppresses category routing. The item is
unrouted even when its category has an active route, and the order continues to
be accepted without a kitchen ticket. This is intentional precedence behavior,
but it is operationally risky: deactivating a station can silently make an
overridden item disappear from the kitchen.

Operators with Owner/Admin/Manager access to a branch can call
[`public.list_kitchen_routing_issues(branch_id)`](#rpc-signatures) to inspect:

- inactive item-level routes, including whether an active category route exists
  (`categoryRouteActive`);
- inactive category-level routes;
- the affected menu item, category, station, and branch context.

The RPC is read-only and never returns routing configuration from another
branch or organization.

## 8. Authorization

The kitchen RPCs reuse the M4.1 branch-role rule:

```text
owner, admin, manager, kitchen_staff
```

- Organization-scoped Owner/Admin/Manager access covers every branch in the
  organization.
- Branch-scoped Owner/Admin/Manager/Kitchen Staff access is limited to assigned,
  active branches.
- Cashier is denied kitchen transitions; cashier keeps its existing M3 order
  acceptance and cancellation permissions.
- Cross-branch kitchen access is denied with `PERMISSION_DENIED`.
- Cross-organization access returns `KITCHEN_TICKET_ITEM_NOT_FOUND` rather than
  leaking record existence.
- Kitchen Staff do not gain access to cashier-only order transitions,
  administrative tables, or subscriptions.
- M4.3 also denies Kitchen Staff the order-level `preparing`/`ready`
  transitions. Kitchen Staff use the ticket-item RPCs instead; Owner/Admin/
  Manager retain the order transitions.
- Authenticated clients still have `SELECT` only on kitchen tables. Direct
  `INSERT`, `UPDATE`, and `DELETE` on kitchen tables are denied; all transitions
  go through the RPCs below.

### RPC signatures

| RPC | Argument | Returns | Authorization |
| --- | --- | --- | --- |
| `public.start_kitchen_ticket_item(uuid)` | ticket item ID | Updated ticket JSON (`jsonb`) | Owner/Admin/Manager/Kitchen Staff in the ticket branch |
| `public.mark_kitchen_ticket_item_ready(uuid)` | ticket item ID | Updated ticket JSON (`jsonb`) | Same |
| `public.complete_kitchen_ticket_item(uuid)` | ticket item ID | Updated ticket JSON (`jsonb`) | Same |
| `public.list_kitchen_routing_issues(uuid)` | branch ID | `{ branchId, issues[] }` (`jsonb`) | Owner/Admin/Manager in the branch |

Each transition RPC returns the full ticket, including its items and aggregate
status, so the client can update the KDS view without a second query. Ticket JSON
includes `generation`, `cancelledByActorType`, and `cancelledByStaffId`; ticket
item JSON includes the same cancellation actor fields. The private transitions
and generation helpers are not executable by client roles.

`list_kitchen_routing_issues` is read-only. It raises `BRANCH_NOT_FOUND` for a
branch outside the caller's organization and `PERMISSION_DENIED` for Cashier,
Kitchen Staff, or an inaccessible branch. Issue objects use
`issueType = 'inactive_item_route'` with `categoryRouteActive`, or
`issueType = 'inactive_category_route'`.

## 9. Audit

Kitchen lifecycle audit uses the existing append-only `public.audit_events`
table and `private.audit_write`:

| Action | Target | Metadata |
| --- | --- | --- |
| `kitchen.ticket_created` | `kitchen_ticket` | `order_id`, `station_id`, `generation`, `status` |
| `kitchen.ticket_status_changed` | `kitchen_ticket` | `order_id`, `station_id`, `generation`, `from_status`, `to_status`; cancellation events also include `cancelled_by_actor_type` and `cancelled_by_staff_id` |
| `kitchen.ticket_item_status_changed` | `kitchen_ticket_item` | `ticket_id`, `order_id`, `order_item_id`, `from_status`, `to_status`; cancellation events also include `cancelled_by_actor_type` and `cancelled_by_staff_id` |

The actor is the authenticated staff member when available; trusted
backend/system writes without a staff identity use the `system` actor type.
For cancellation events, audit uses the cancellation actor recorded on the
ticket or ticket item, so staff and system cancellations remain consistent with
the persisted row. Cancellation events also record the cancellation reason.

## 10. M3 compatibility

- The M3 order lifecycle was not redesigned. The final corrective migration
  narrowly replaces `public.remove_order_item` so that an order already in
  `preparing` or `ready` can remove an item whose matching kitchen items are
  still `pending`/`preparing`/`ready`; terminal orders and completed kitchen
  work remain blocked.
- The replacement uses a transaction-local subtotal-recalculation exception in
  the existing M3 order snapshot guard. Order totals are not generally editable
  after preparation starts.
- M4.2 integration is additive: order/item triggers, ticket-item aggregate
  trigger, and private functions.
- Kitchen RPCs never update `orders` or `order_items`, so kitchen progress cannot
  move an order backward or bypass cashier transitions.
- M3's order status cascade updates `order_items.status` only; it cannot
  overwrite `kitchen_ticket_items.status`.
- M3 terminal-state guards, order/item timestamps, cancellation requirements,
  and role authorization remain unchanged.
- M4.3 narrows only the order-level `preparing`/`ready` role array:
  Owner/Admin/Manager retain the transitions; Kitchen Staff are denied and must
  use the kitchen ticket-item RPCs. Other order transitions and roles are
  unchanged.
- An order with no routed kitchen items can still be accepted, prepared, served,
  and completed through the existing M3 lifecycle.

## 11. Known limitations

- Route changes made after acceptance apply to items added later; existing
  active tickets are not retroactively rerouted. A cancelled station ticket is
  preserved, and later routed work receives a new generation.
- Multiple active routes for the same item create work on each station. There is
  no per-route quantity split or cross-station aggregate.
- Ticket aggregation can move to a lower aggregate state when a new pending item
  is added to an accepted order or when a progressed item is cancelled. Status
  consumers must tolerate regression; first-set timestamps are not cleared.
- Completed kitchen work cannot be removed through item removal. It can still be
  cancelled as part of whole-order cancellation, with the order cancellation
  actor and reason; the audit trail retains the earlier completion transitions.
- Removing an item from a `preparing`/`ready` order can leave the order with no
  active items. Such an order cannot be served or completed; it must be cancelled.
- Direct ticket-item writes are a trusted/privileged boundary. Authenticated
  clients have `SELECT` only. The database recalculates aggregate status and
  rejects active items under cancelled tickets, but direct writes remain outside
  the supported application API.
- Inactive item-level routes intentionally suppress category fallback. Operators
  must use `list_kitchen_routing_issues` or monitor unrouted orders to detect the
  operational risk.
- M3 order cancellation requires a staff actor. Kitchen rows can represent
  system-initiated cancellation through privileged order-item or kitchen write
  paths, but there is no client-callable system cancellation RPC.
- Station-specific staff assignment and station-level ticket filtering remain
  deferred. Kitchen Staff have branch-wide access.
- Realtime publication and the channel contract are implemented, but delivery
  and branch-isolation tests are blocked until a local Supabase/Docker stack is
  available. `BLK-008` remains open and polling is the supported fallback.
- Completed/cancelled history requires an explicit status request and a bounded
  `from`/`to` window of at most 31 days.
- Kitchen ticket history becomes unreadable after a branch is deactivated
  because kitchen RLS/RPC authorization requires an active branch. This is an
  acknowledged limitation, not a new retention policy.
- The KDS frontend is not part of this repository.

## 12. M4.3 — KDS read API and ownership policy

### 12.1 Read RPCs

| RPC | Purpose | Authorization |
| --- | --- | --- |
| `public.list_kitchen_tickets(p_branch_id, p_station_id, p_statuses, p_limit, p_offset, p_from, p_to)` | Bounded branch/station board, oldest first. | Owner/Admin/Manager/Kitchen Staff in the branch; Cashier denied. |
| `public.get_kitchen_ticket(p_ticket_id)` | One complete ticket view. | Same branch rule; cross-organization returns `KITCHEN_TICKET_NOT_FOUND`. |
| `public.list_kitchen_stations(p_branch_id)` | Stations and routing configuration. | Owner/Admin/Manager/Kitchen Staff read; Cashier denied. |

`list_kitchen_tickets` defaults to `pending`, `preparing`, and `ready`, orders by
`created_at asc, id asc`, enforces `1 <= limit <= 100`, and returns
`pageSize`, `hasMore`, and `nextOffset`. Completed and cancelled statuses require
an explicit `from`/`to` window no longer than 31 days. An empty status array,
negative offset, reversed window, or oversized history window returns
`VALIDATION_ERROR`.

Each ticket response contains:

- ticket identity, `generation`, aggregate status, and lifecycle timestamps;
- station ID and station name;
- order ID, reference, status, source, accepted timestamp, and notes;
- table ID and `restaurant_tables.label` (nullable when unavailable);
- ticket items with order-item/menu-item identity, name, quantity, notes,
  kitchen status, timestamps, cancellation attribution, and modifier snapshots;
- `createdAt`/`updatedAt` on tickets and items for reconciliation.

The response contains **no** item prices, subtotals, discounts, order totals,
currency, or payment data. The KDS is an operational surface only.

The transition RPCs keep returning the M4.2 ticket JSON shape. A KDS that wants
the full board shape should call `get_kitchen_ticket` after a transition. This
avoids changing the M4.2 contract.

### 12.2 Station and routing management

Owner/Admin/Manager in the station branch can call:

```sql
public.create_kitchen_station(p_branch_id uuid, p_name text, p_description text default null)
public.update_kitchen_station(p_station_id uuid, p_name text, p_description text default null)
public.deactivate_kitchen_station(p_station_id uuid, p_reason text default null)
public.reactivate_kitchen_station(p_station_id uuid)
public.add_kitchen_station_category_route(p_station_id uuid, p_menu_category_id uuid)
public.remove_kitchen_station_category_route(p_station_id uuid, p_menu_category_id uuid)
public.add_kitchen_station_item_route(p_station_id uuid, p_menu_item_id uuid)
public.remove_kitchen_station_item_route(p_station_id uuid, p_menu_item_id uuid)
```

Behavior:

- Station names are unique per branch using the existing case-insensitive,
  trimmed comparison. Duplicates return `RESOURCE_CONFLICT`.
- Duplicate category/item routes return `RESOURCE_CONFLICT`. Removing a missing
  route also returns `RESOURCE_CONFLICT`.
- A route cannot be added to an inactive station (`KITCHEN_STATION_INACTIVE`).
  Existing routes can still be removed while the station is inactive.
- Cross-organization or missing station references return
  `KITCHEN_STATION_NOT_FOUND`; cross-organization menu references return
  `MENU_ITEM_NOT_FOUND`.
- Deactivation sets `status = 'inactive'` and `deactivated_at`; reactivation
  clears it. Both are idempotent no-ops when the station is already in the target
  state.
- Deactivation does not cancel existing tickets. Existing tickets remain
  readable and completable, and reactivation restores the existing routes.
- Every write is audited with `private.audit_write` under
  `kitchen.station_*` or `kitchen.*_route_*` actions.
- There is no station delete RPC. Stations with tickets are retained.

### 12.3 Order versus kitchen state ownership

- POS/order operations own the order lifecycle.
- Kitchen Staff own kitchen ticket and ticket-item preparation.
- Kitchen item completion does **not** mark an order served, completed, or paid.
- Kitchen ticket transitions do not mutate `orders` or `order_items`.
- Order transitions cascade `order_items.status` only; they do not mutate
  `kitchen_tickets` or `kitchen_ticket_items`.
- Kitchen Staff cannot use `transition_order_status` for order-level
  `preparing` or `ready`. Owner/Admin/Manager retain those transitions. All other
  roles and targets are unchanged.
- Starting the first kitchen item is the v1 acknowledgement signal. There is no
  explicit ticket acknowledgement state.

### 12.4 Realtime

The kitchen publication, branch channel, filters, and recovery behavior are
defined in [`realtime-architecture.md`](./realtime-architecture.md). Ticket and
ticket-item events are both required. Delivery and branch isolation remain
unverified in this environment; `BLK-008` stays open and polling is supported.
